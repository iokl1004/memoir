# Spring Boot에서 Supabase + Vercel로 옮긴 기록

2026년 11월, 배포 직전에 백엔드를 통째로 바꿨어요. 기능과 화면은 그대로 두고, 서버만 바꿨어요.
Spring 버전의 마지막 코드는 커밋 [`3fc7d07`](https://github.com/iokl1004/memoir/tree/3fc7d07)에 있어요.

## 1. 배경: 무료로 띄울 곳이 없었어요

조건은 **완전 무료로 배포**하는 것이었어요. Spring Boot 버전은 이런 서버가 필요했어요.

- JVM이 늘 켜져 있어야 해요. 메모리는 300~500MB쯤 써요.
- MySQL도 함께 돌려야 해요. 그림까지 DB에 들어 있었어요.

이 조건을 무료로 맞추는 곳은 사실상 **Oracle Cloud Always Free**(ARM 4코어, 24GB)뿐이었어요. 그래서 Docker 묶음(앱 + MySQL + Caddy HTTPS + 백업 스크립트)까지 만들고 로컬 리허설도 끝냈어요.
그런데 **Oracle 한국 리전에서 무료 VM을 받을 수 없었어요.** 언제 열릴지도 알 수 없었어요.

## 2. 검토한 방법

| 방법 | 장점 | 걸린 점 |
|---|---|---|
| Oracle 일본 리전(도쿄·오사카) | 코드를 안 바꿔도 돼요. 한국에서 지연 30ms 정도 | 무료 VM은 가입할 때 고른 **홈 리전에만** 만들 수 있고, 홈 리전은 **나중에 바꿀 수 없어요.** 한국 리전이 열려도 옮길 수 없어요 |
| Render 무료 | Docker 그대로 올라가요 | 15분 쉬면 잠들어요. Spring은 깨어나는 데 30초가 넘어요. DB는 따로 구해야 해요 |
| Cloudflare(Workers + D1 + R2) | 잠들지 않고 빨라요 | DB가 SQLite라서 스키마와 쿼리를 크게 바꿔야 해요 |
| **Supabase + Vercel** | Auth, Storage, Postgres, 함수를 한 번에 줘요. **서울 리전**이 있어요 | 7일 쉬면 일시 정지, 자동 백업 없음, 저장소 1GB |

## 3. 결정: Supabase(서울) + Vercel

- 일본 리전은 "한 번 고르면 영영 못 바꾸는" 선택이라 부담이 컸어요.
- Supabase는 Spring이 하던 일(로그인, 세션, 메일, 캡차, 파일 저장)을 대부분 기본 기능으로 줘서, 직접 운영할 서버(보안 패치, 인증서, 백업)가 없어져요.
- 무료 한도의 약점(일시 정지, 백업 없음)은 GitHub Actions 하나로 함께 막을 수 있었어요(아래 5).

무료 한도를 memoir에 맞춰 따져 봤어요. 메모 글자는 작아서 DB 500MB는 넉넉하고, 문제는 그림이었어요. 캡처 한 장을 넉넉히 500KB로 잡으면 1GB에 약 2,000장이에요. 그래서 한 사람의 그림 한도를 200MB에서 **50MB(약 100장)**로 낮추고, 계정 창에 얼마나 썼는지 보여주게 했어요.

## 4. 옮기면서 바꾼 설계

| Spring 버전 | Supabase 버전 | 바꾼 이유 |
|---|---|---|
| 서비스 계층에서 `user_id`로 주인 확인 | **RLS** (`user_id = auth.uid()`) | 화면이 DB에 직접 붙으니, 주인 확인이 DB에 있어야 해요 |
| 서비스 코드의 규칙(미분류 보호, 순환 금지) | **트리거** | 함수를 거치지 않고 표를 직접 고쳐도 규칙이 지켜져요 |
| `@Transactional` 서비스 메서드 | **PL/pgSQL 함수**(`supabase.rpc`) | 여러 줄을 함께 바꾸는 일은 함수 하나 = 트랜잭션 하나 |
| Spring Session JDBC + CSRF | Supabase Auth (JWT) | 쿠키 세션이 아니라서 CSRF 토큰이 필요 없어요 |
| 로그인 5번 틀리면 캡차 (`LoginThrottle`) | 가입·로그인·패스워드 찾기에 **항상** Turnstile | Supabase는 "N번 틀린 뒤에만"을 지원하지 않아요. Turnstile은 대부분 누르지 않아도 풀려서 불편이 적어요 |
| jsoup으로 서버에서 HTML 정리 | **TipTap 스키마**가 정리 | 화면이 DB에 직접 쓰니 서버 정리를 하려면 저장마다 함수를 거쳐야 해요. 메모는 주인만 보니, 나쁜 HTML이 들어가도 피해가 본인에게만 가요. 공유 기능을 넣으면 서버 정리를 다시 넣어요 |
| 그림을 DB(BLOB)에 저장, `/api/images/{id}` | **비공개 Storage** + 본문엔 `/img/{id}`, 보여 줄 때 **서명 주소** | 비공개 파일은 기한이 있는 주소로만 볼 수 있어요. 본문에는 바뀌지 않는 번호만 두고, 같은 서명 주소를 1시간 재사용해서 브라우저 캐시와 전송량(월 5GB)을 아껴요 |
| 서버(ImageIO)에서 그림 줄이기 | **브라우저**(canvas)에서 줄여서 올리기 | 함수의 CPU와 전송량을 아껴요. 덤으로 휴대폰 사진의 회전 문제가 사라지고 위치 정보(EXIF)도 빠져요 |
| 업로드 API에서 형식·용량 확인 | **upload-image Edge Function** | 브라우저는 믿을 수 없어서 형식(파일 앞부분), 5MB, 50MB 한도는 서버에서 봐요. Storage 정책(RLS)으로는 합계 용량을 볼 수 없어요 |
| `@Scheduled` 고아 그림 청소 | **cleanup-images 함수**를 Actions가 매일 호출 | Storage 파일은 SQL로 지우면 파일이 남아서, Storage API로 지워야 해요 |
| 계정 삭제 (서비스 코드) | **delete-account 함수** | 사용자 삭제는 관리자 키가 필요하고, 그림 파일이 남아 있으면 사용자를 지울 수 없어서 파일부터 지워요 |
| MySQL `LIKE` / `FULLTEXT ngram` 자동 선택 | Postgres `ILIKE` | 50만 건에서 재 보고 고른 방식이었지만, 개인 메모 규모(수천 건)에서는 `ILIKE`로 충분해요. 느려지면 `pg_trgm` 인덱스를 붙여요 |
| `@Async` 메일 + 해시 토큰 테이블 | Supabase Auth의 패스워드 찾기 | 링크는 `token_hash` 방식이라 다른 기기에서 열어도 돼요. 가입 여부를 숨기는 응답도 그대로예요 |
| 서버 디스크 백업(cron + mysqldump) | **daily.yml**: `pg_dump` + 그림 파일 → 암호화 → Actions 결과물 | 저장소가 공개라 결과물은 누구나 받을 수 있어서 반드시 암호화해요. 매일 DB를 써서 7일 일시 정지도 막아요 |
| JUnit + Testcontainers(MySQL) 91개 | Vitest + 로컬 Supabase 13개 | RLS로 남의 메모가 안 보이는지, 함수와 Edge Function이 맞게 도는지를 실제 Supabase에 대고 확인해요. CI도 러너에서 Supabase를 띄워요 |

## 5. 잃은 것과 얻은 것

**잃은 것**
- Java/Spring 코드와 테스트 91개, Docker 배포 묶음 (git 기록에는 남아 있어요)
- MySQL 검색 성능 측정(LIKE vs FULLTEXT, 50만 건)과 자동 선택 검색. Spring 버전의 `bench/README.md`에 결과가 남아 있어요
- "5번 틀린 뒤에만 캡차" 같은 세밀한 로그인 제한

**얻은 것**
- 운영할 서버가 없어요. 보안 패치, HTTPS 인증서, 디스크 관리가 사라졌어요
- 서울 리전에서 지금 바로 무료로 배포할 수 있어요
- 권한 검사가 DB(RLS)에 있어서, 앞으로 기능을 늘려도 주인 확인을 빼먹을 일이 줄어요

**남은 위험과 대응**
- 7일 쉬면 일시 정지 → 매일 도는 Actions가 DB를 써요
- 자동 백업 없음 → 매일 암호화 백업, 14일 보관
- 저장소 1GB, 전송량 월 5GB → 한 사람 50MB 한도, 올리기 전 줄이기, 서명 주소 재사용
